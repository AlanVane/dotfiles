你自己说出来的六条

  • hook 的权力来自你写的退出码，git 只是执行者；打印什么不影响判决。
  • pre- 能拦，post- 只能看：post-commit 里 exit 1 时账已经记完。
  • commit-msg 是唯一能碰消息的关卡，它拿到的是消息文件路径。
  • hook 不在任何一本账上——不在对象库、不在引用、不在工作区，所以 clone 带不走它。
  • core.hooksPath 只解决「内容不漂」，那行 config 仍要每人一次；husky 用 npm prepare 补后半。
  • 本地永远有缺口（不装依赖 / 不跑脚本 / --no-verify），只有服务端 pre-receive 是强制。

要点：钩子的真实位置

  • git 不查账本找钩子，只按固定路径看一眼：有可执行文件就跑，没有就跳过（提示是贴心，不是关卡）。
  • 钩子的 cwd 永远是仓库根，跟你敲命令时在哪个子目录无关。
  • 提交对象生成前 index 仍可改，所以「格式化 + git add」能进这次提交——忘了 add 就提交旧版本。

留的尾巴

  • 误解 #1（待换形）：以为 hook 没执行位时 git 会报错拦你——实测是「提示 + 放行」，且提示可关。
  • 新变体：把 husky 当强制。首答「存在即生效」，靠与前两答对账自破。
  • 标签弱项：commit-msg 与 pre-receive 混过一次（客户端 / 服务端），与 submodule 的 160000 同型。
  • 未覆盖：pre-push 的 stdin 协议、服务端 update 逐 ref 调用。
